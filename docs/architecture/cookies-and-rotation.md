# Cookie Encryption and Key Rotation Architecture

## Executive Summary

This document describes the architecture for cookie encryption and automatic key rotation in the Pika Framework. The system uses AWS KMS-backed rotating data encryption keys (DEKs) using the envelope encryption pattern, with automatic 12-hour rotation cycles.

**Key Benefits:**

- Enhanced security through regular key rotation
- No hardcoded secrets in code or configuration
- Graceful handling of key rotation without user disruption
- Support for both local development and production deployment
- Comprehensive monitoring and error recovery

### Security Requirements

The system addresses these requirements:

- **Regular Key Rotation**: Keys rotate automatically every 12 hours
- **Zero Downtime**: Users remain authenticated during key rotation
- **Secure Key Management**: All keys managed by AWS KMS
- **No Hardcoded Secrets**: All encryption keys generated and managed dynamically
- **Audit Trail**: All key operations logged and trackable

## Conceptual Architecture

### Envelope Encryption Pattern

The system implements AWS's recommended envelope encryption pattern:

```
┌─────────────────────────────────────────────────────────────┐
│                    Envelope Encryption                      │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  ┌─────────────┐    encrypts   ┌─────────────────────────┐  │
│  │   KMS Key   │ ────────────► │  Data Encryption Key    │  │
│  │  (Master)   │               │      (DEK) v1           │  │
│  └─────────────┘               └─────────────────────────┘  │
│                                                             │
│  ┌─────────────────────────────┐   encrypts    ┌─────────┐  │
│  │  Data Encryption Key (DEK)  │ ────────────► │ Cookie  │  │
│  │      (Plaintext)            │               │  Data   │  │
│  └─────────────────────────────┘               └─────────┘  │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**Key Principles:**

1. **KMS Master Key**: Never leaves AWS, used only to encrypt/decrypt DEKs
2. **Data Encryption Keys (DEKs)**: 256-bit AES keys generated by KMS
3. **Versioned Storage**: Multiple DEK versions stored simultaneously
4. **In-Memory Caching**: Plaintext DEKs cached in application memory
5. **Secure Transport**: Encrypted DEKs stored in SSM Parameter Store

### Cookie Versioning Strategy

Cookies use a versioned format to support seamless key rotation:

```
Format: {version}:{iv_hex}:{encrypted_data}
Example: 1:a1b2c3d4e5f6....:f8e9d0c1b2a3....
```

**Components:**

- **Version**: Integer identifying which DEK version was used (1-100, cycles)
- **IV (Initialization Vector)**: 16-byte random value, unique per encryption
- **Encrypted Data**: AES-256-CBC encrypted JSON payload

**Version Management:**

- Multiple versions active simultaneously (typically 3)
- New cookies encrypted with current version
- Old cookies decrypted using cached versions
- Automatic version cleanup after rotation

## Technical Architecture

### Core Components

#### 1. KeyManager Class

**Location**: `src/lib/server/encryption/KeyManager.ts`

**Responsibilities:**

- Manages in-memory cache of plaintext DEKs
- Automatic key refresh based on configurable interval
- Graceful fallback to cached keys if refresh fails
- Thread-safe initialization and refresh operations

**Key Features:**

```typescript
class KeyManager {
    // In-memory cache of version -> plaintext key
    private keyCache: Map<number, Buffer>;

    // Current encryption version
    private currentVersion: number;

    // Automatic refresh every N hours (configurable)
    private refreshIntervalMs: number;

    // Key methods
    async initialize(): Promise<void>;
    async refreshKeysIfNeeded(): Promise<void>;
    getCurrentKey(): Buffer;
    getKeyCache(): Map<number, Buffer>;
}
```

#### 2. CookieEncryption Class

**Location**: `src/lib/server/encryption/CookieEncryption.ts`

**Responsibilities:**

- Versioned cookie encryption and decryption
- Unique IV generation per encryption operation
- Support for multiple key versions simultaneously
- Validation and error handling

**Key Features:**

```typescript
class CookieEncryption {

    encrypt(data: string, version: number, key: Buffer): string;

    // Version extraction and validation
```

### Infrastructure Components

#### 1. Key Rotation Lambda Function

**Location**: `infra/lambda/cookie-key-rotation/`

**Purpose**: Scheduled key rotation every 12 hours

**Key Features:**

- EventBridge-triggered execution (12-hour schedule)
- Force rotation capability for manual invocation
- Distributed locking to prevent concurrent executions
- Comprehensive error handling and recovery

**Flow:**

1. Check if rotation is needed (time-based)
2. Acquire distributed lock in SSM
3. Generate new DEK using KMS
4. Store encrypted DEK in SSM
5. Update version tracking parameters
6. Clean up old versions
7. Release lock

#### 2. Key Initializer Lambda Function (CloudFormation Custom Resource)

**Location**: `infra/lambda/cookie-key-initializer/`

**Purpose**: Initialize encryption infrastructure on stack deployment

**Key Features:**

- CloudFormation custom resource pattern
- Creates KMS keys and aliases with proper policies
- Initializes first set of encryption keys
- Idempotent operations (safe to run multiple times)
- Handles CloudFormation lifecycle (Create/Update/Delete)

**Flow:**

1. Create KMS key with appropriate policies
2. Create KMS alias for easy reference
3. Invoke rotation function for initial key setup
4. Store key alias in SSM for application reference
5. Report success/failure to CloudFormation

#### 3. Cookie Encryption Setup Tool

**Location**: `tools/cookie-encryption-setup/`

**Purpose**: Local development infrastructure setup

**Key Features:**

- CLI tool for local development
- Creates same infrastructure as CloudFormation
- Status checking and reporting
- Idempotent operations
- Helpful error messages and guidance

**Commands:**

```bash
# Check current infrastructure status
pnpm run encryption:setup -- status

# Create infrastructure if missing
pnpm run encryption:setup -- setup
```

### Security Model

#### Key Management Security

**KMS Master Key Protection:**

- Master key never leaves AWS KMS
- Customer-managed key with appropriate policies
- Key rotation enabled at KMS level
- Resource-based access control using IAM conditions

**DEK Security:**

- 256-bit AES keys generated by KMS
- Encrypted at rest in SSM Parameter Store
- Plaintext keys cached only in application memory
- Automatic cleanup of old versions

**Access Control:**

```json
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Effect": "Allow",
            "Principal": { "AWS": "arn:aws:iam::ACCOUNT:role/ECS-Task-Role" },
            "Action": ["kms:GenerateDataKey", "kms:Decrypt"],
            "Resource": "*",
            "Condition": {
                "StringEquals": {
                    "aws:ResourceTag/Project": "project-name",
                    "aws:ResourceTag/Purpose": "CookieEncryption"
                }
            }
        }
    ]
}
```

#### Operational Security

**Rotation Timing:**

- 12-hour rotation interval balances security and performance
- Cookie expiration aligned with rotation schedule
- 3 active key versions provide overlap for edge cases

**Concurrency Protection:**

- Distributed locking prevents concurrent rotations
- Lock timeout prevents deadlocks (5-minute TTL)
- Graceful handling of race conditions

**Error Recovery:**

- Application continues with cached keys if refresh fails
- Comprehensive logging for troubleshooting
- Health check endpoints for monitoring

### Performance Characteristics

#### Memory Usage

**Key Cache:**

- Approximately 32 bytes per active key version
- Maximum 3 versions = ~100 bytes total
- Negligible impact on application memory

**Initialization Time:**

- Cold start: ~200-500ms for key loading
- Warm start: Immediate (keys already cached)
- Batch parameter retrieval for optimization

#### Encryption Performance

**Cookie Operations:**

- Encryption: ~1ms per cookie (includes IV generation)
- Decryption: ~0.5ms per cookie (cached key lookup)
- No performance regression vs previous system

**Refresh Operations:**

- Background refresh every hour (configurable)
- Non-blocking operation (uses cached keys on failure)
- Optimized batch parameter retrieval

**Infrastructure Missing:**

#### Recovery Procedures

**Corrupted Key Cache:**

- Application restart clears cache and reloads from SSM
- Health check endpoints help identify cache issues
- Automatic cache validation on startup

**Failed Key Rotation:**

- Manual rotation trigger available via Lambda invocation
- Lock breaking for stale locks (5-minute timeout)
- Rollback procedures for critical failures
